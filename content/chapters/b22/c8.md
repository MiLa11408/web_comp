## 一句话

2023 年起，vLLM 用分页显存（按块借还显存）把机房吞吐拉高，llama.cpp 用 C/C++ 与低比特量化把模型塞进笔记本，Ollama 再把下载、运行和 API 包成一条命令——开源权重从此不只拿得到，还跑得动。

## 时间·人物·机构

2023 年 9 月 12 日，加州大学伯克利分校的 Woosuk Kwon、Zhuohan Li、Siyuan Zhuang、Ying Sheng、Lianmin Zheng、Cody Hao Yu、Joseph E. Gonzalez、Hao Zhang、Ion Stoica 提交《Efficient Memory Management for Large Language Model Serving with PagedAttention》，论文入选 SOSP 2023，并公开 vLLM 源码。几乎同一时间，Georgi Gerganov 发起的 llama.cpp 把推理写成不依赖第三方库的纯 C/C++，支持 Apple Silicon 的 Metal、ARM NEON 与 Accelerate，x86 的 AVX、AVX2、AVX512、AMX，以及 CUDA、HIP、MUSA、Vulkan、SYCL、WebGPU 等后端。Ollama 则把 llama.cpp 包在更上层：命令行一条 `ollama` 就能拉模型、跑对话，本地 REST API 监听 11434 端口；官网称其月安装量 900 万以上、模型下载 10 亿次以上、累计服务 200 万亿 token，并写明提示词不会被存储或用于训练。

## 为什么是这个时候

大模型在 2023 年同时撞上两件事：一边是权重开始外流与开放，LLaMA 系列让「在自己机器上跑模型」从极客玩具变成正经需求；另一边是服务端显存成了瓶颈。vLLM 论文说得很直白：每个请求的键值缓存（key-value cache，KV cache）又大又会动态伸缩，管理不善就被碎片和重复占满，batch 开不大，吞吐上不去。llama.cpp 面对的是另一种现实：GPU 型号杂、内存有限、用户不想为一次推理装一整套 Python 栈。Ollama 则解决「最后一公里」——模型文件、运行参数、接口协议各说各话，普通用户需要一个统一入口。三者的共同前提是：权重大量可得、消费级硬件显存够大、社区愿意长期维护开源实现。

## 怎么工作

vLLM 的核心是 PagedAttention（分页注意力）。它借操作系统的虚拟内存与分页思路，把每个请求的 KV 缓存切成固定大小的块，按需分配、按块寻址，不再要求一整段连续显存；块还能在同一请求内、甚至跨请求共享，于是浪费接近零，batch 可以开得更大。论文给出的结果是：在相同延迟下，吞吐比 FasterTransformer、Orca 这类当时的最优系统高 2–4 倍，序列越长、模型越大、解码越复杂，差距越明显。大白话：以前每桌客人先占一张四人桌，哪怕只来一个人；PagedAttention 把桌子改成可拼的桌板，按人头给板子——准确地说，是把 KV 缓存分页管理、按需映射，减少碎片与重复。

llama.cpp 干的是「把模型塞进你的硬件」。它用 1.5、2、3、4、5、6、8 比特整数量化压缩权重；显存不够时让 CPU 与 GPU 混合推理，把超出显存的那部分层留给内存；后端覆盖 Metal、NEON、Accelerate、CUDA、HIP、MUSA、Vulkan、SYCL、WebGPU。大白话：把一整箱货拆成小包，按你后备箱的格子和承重往里塞——准确地说，是量化降低每参数位宽，并按层切分计算图，让 CPU 与 GPU 各跑一部分。

Ollama 把上述能力收进一条命令：`ollama` 启动后按提示选模型，REST API 用 `/api/chat` 收发消息，Python 与 JavaScript 都有官方库；模型默认留在本地。大白话：像给模型装了一个应用商店加电源键——准确地说，是提供模型拉取、运行、版本管理与本地 HTTP 接口的一体化封装，底层仍是 llama.cpp。

## 它改变了什么

第一，机房的服务方式变了。PagedAttention 之后，「KV 缓存怎么管」从实现细节变成服务框架的核心指标；vLLM 源码公开，让中小团队不必从零写调度器。第二，个人电脑重新成为推理设备：4 比特量化让十亿级参数模型能在笔记本上跑，Apple Silicon 的统一内存成了意外赢家；这直接改变了隐私叙事——数据不出本机。第三，产品门槛被压到一条命令：Ollama 的月安装量与下载量说明，「本地大模型」从论文附录变成了桌面软件。第四，成本结构变了：云端按 token 计费，本地按电费和硬件折旧计费，二者在低频、隐私敏感场景里出现交叉点。第五，部署成了开源生态的「第四层」：权重、数据、许可证之后，能不能跑、跑多快、好不好维护，开始决定一个开放模型的实际采用率。第六，运维语言变了：从「装环境」变成「选量化、配后端、看显存」——门槛低了，但门槛只是换了个位置。

## 今天的地位

判定：三件都还在用，但各自的天花板已经看得见。vLLM 是数据中心批量推理的常用底座，论文里的 2–4 倍是相对 2023 年的 FasterTransformer 与 Orca，不是对今天所有框架的承诺；llama.cpp 是本地推理与量化格式的参考实现，后端名单还在变长，代价是维护面越来越宽；Ollama 是桌面与个人开发者最省事的入口，但它的抽象也把调参、监控和多租户留给了更专业的部署层。它们没有取代彼此，而是把「部署」切成了机房、设备、桌面三段。对个人用户，一条命令是解放；对机房，抽象少一层就多一分可控。

## 争议与局限

第一，vLLM 的收益有前提：batch 小、序列短、模型小时，分页管理的额外开销可能吃掉一部分吞吐；显存共享带来的复杂度，也要求运维看得懂块表。第二，量化不是免费的午餐：1.5–2 比特能把模型压得很小，但精度损失在推理、代码、长上下文任务上更明显；4 比特通常是质量与体积的折中，不是无损。第三，本地推理的速度上限由内存带宽决定，笔记本能跑不等于能快跑。第四，Ollama 的「数据不保留」是产品承诺，具体是否成立取决于部署方式与网络配置，不能替代合规审查。第五，生态碎片化：格式、兼容层与 API 方言仍在分裂，「一次导出、处处运行」还是个愿望。第六，安全责任随权重一起下放：任何人都能本地微调、去掉对齐，发布方难以撤回。
