## 一句话

2023 年 6 月 OpenAI 在 Chat Completions API 里加入函数调用，模型不再只回一段话，而是按函数说明吐出带参数的 JSON 让程序执行；2024 年 11 月 Anthropic 把这种连接标准化成 MCP（模型上下文协议），模型从「会说」变成「能插上外部世界」。

## 时间·人物·机构
模型能写出一封漂亮的邮件，却发不出去——2023 年之前，它被关在自己的参数里。函数调用给了它一双手。

2023 年 6 月 13 日，OpenAI 发布《Function calling and other API updates》，把函数调用加进 Chat Completions API，首批支持 gpt-4-0613 与 gpt-3.5-turbo-0613；同一批更新里还有 16k 上下文的 gpt-3.5-turbo、嵌入模型降价 75%、gpt-3.5-turbo 输入 token 降价 25%。2024 年 11 月 25 日，Anthropic 开源 MCP，作者是 David Soria Parra 与 Justin Spahr-Summers；官方介绍把它定位为「连接 AI 助手与数据所在系统」的开放标准，架构分 MCP 服务器与 MCP 客户端两侧。

## 为什么是这个时候

模型在 2023 年已经能写会算，但它被关在自己的参数里：不知道你的日历、数据库和仓库，也不会真的发邮件。早期的补救办法是提示词工程——让模型输出「Action: search(...)」这样的文本，再用人写正则去解析；格式一歪，整条链就断。函数调用换了个思路：开发者先用 JSON Schema 描述函数名、参数类型和必填项，模型被微调成「该调用时输出符合签名的 JSON」，程序拿到的就不是散文，而是可解析的对象。打个比方，旧办法像让厨师听一段口头描述再猜你要什么；函数调用像给一张标准点菜单，菜名、辣度、忌口都有固定栏位。准确地说，JSON Schema 把自然语言意图约束成结构化参数，模型负责选函数与填值，执行权仍在应用手里。到 2024 年，问题从「怎么调用一个工具」变成「怎么接上几百个工具」：每个应用给每个数据源写一套连接器，M 个应用乘 N 个工具就是 M×N 份适配代码；MCP 想把这件事压成 M+N。

## 怎么工作

函数调用的流程是三步。第一步，应用把用户问题和函数清单一起发给模型，清单里写明 `get_current_weather(location: string, unit: 'celsius' | 'fahrenheit')` 这类签名。第二步，模型判断要不要调用，若需要，就返回一个 `function_call`，里面有函数名和参数，例如 `{"location": "Boston, MA"}`，结束原因是 `function_call`。第三步，应用真的去调天气 API，拿到 `{"temperature": 22, "unit": "celsius"}`，再把结果塞回对话，让模型总结成一句人话。官方举的例子还有：把「给 Anya 发邮件约咖啡」转成 `send_email(to, body)`，把「本月客户前十名」转成内部 API 或 SQL 查询。

MCP 则把「工具」做成可插拔的插座。服务器把数据源、工具或工作流暴露出来；客户端（Claude Desktop、IDE、聊天应用）连上去，就能在同一套协议下取用。官方给的类比是 USB-C：一个标准口，接很多设备。发布时已经有一批现成服务器，覆盖 Google Drive、Slack、GitHub、Git、Postgres 和 Puppeteer；Block、Apollo 是早期采用者，Zed、Replit、Codeium、Sourcegraph 在开发工具侧接入。用大白话讲：函数调用是「这家店有自己的点菜单」，MCP 是「所有店共用同一个外卖平台接口」——前者解决一单，后者解决整条街。准确地说，函数调用规定单次调用的参数结构，MCP 规定客户端与服务器之间发现、描述和调用工具的协议。MCP 服务器暴露的不只是函数，还包括数据源与专用工作流；协议规范与 SDK 一并发布，本地服务器先在 Claude Desktop 落地。

## 它改变了什么

第一，Agent 从演示变成工程。模型输出可解析的 JSON 之后，重试、校验、日志和权限才有地方挂；「模型提议、程序执行」的分工稳定下来。第二，集成成本换了算法：从每个应用单独适配，变成围绕一个协议写服务器与客户端；工具提供方写一次，多个客户端复用。第三，产品形态变了：插件、连接器、IDE 里的工具面板，底层都在做同一件事——把外部能力编进对话。第四，安全成为显性议题：模型能读日历、发消息、查数据库，权限边界、工具返回内容里的注入、以及「谁批准这次调用」都必须写进设计；MCP 官方文档专门把安全实践单列。第五，接口标准化反过来影响了模型训练：函数调用从「提示技巧」变成模型要学的能力，JSON 格式的稳定性成了评测项。从 2023 年的单个 API 参数，到 2024 年的跨客户端协议，工具调用用了不到一年半，就从「厂商特性」变成「公共接口」。

## 今天的地位

判定是「函数调用已是基础设施，MCP 正在成为连接层的通用语」。主流模型 API 普遍提供工具调用接口，差别在 schema 方言、并行调用与错误处理；MCP 则由 Claude、ChatGPT、VS Code、Cursor 等客户端支持，生态从「每家自己写连接器」转向「写一个服务器到处能用」。但协议只解决插头，不解决插座里的电：工具本身准不准、有没有权限、返回的内容能不能信，仍要应用自己兜。今天的 Agent 框架大多把工具调用当默认件，MCP 则更像 2024 年之后新增的那层「公共插座」。

## 争议与局限

第一，可靠性的边界。OpenAI 的原话是「更可靠地」连接外部工具，不是「绝对可靠」；模型仍可能选错函数、漏填参数、把字符串塞进数字栏。第二，语义不是 schema 能管住的：参数类型对了，含义可能错，比如日期格式合法但时区错了。第三，安全面变大：工具返回的网页、邮件、文件都可能藏着指令注入；把外部内容当可信输入，是这类系统最常见的坑。MCP 文档把安全注意事项单列，说明官方也承认这不是协议自带的能力。第四，生态仍在演化：版本、鉴权、远程服务器的部署方式都在变，今天写的服务器未必明天不用改。第五，成本：每次调用都是一次模型往返加一次外部请求，多工具任务的总延迟会叠起来。
