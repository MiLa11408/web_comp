## 一句话

1980 年代专家系统公司把老师傅的经验写成 IF-THEN 规则（条件判断），卖进 DEC、银行和税务公司；2010 年代云厂商把模型包成 API（按次调用的接口）出租、按调用收费——两次都跑通技术可行，却同样栽在数据、维护、责任、成本四条河上。

## 时间·人物·机构

1980 年，卡内基梅隆大学的 John McDermott 与 DEC 合作，把配置 VAX-11 计算机的规则系统 R1（后称 XCON）送进 DEC 的生产流程；到 1984 年，AI Magazine 已有论文复盘它四年的扩展。1983 年，Edward Feigenbaum 参与创办的 Intellicorp 推出 KEE（Knowledge Engineering Environment），一套跑在 Symbolics、Xerox、TI、Apollo、DEC、Sun、VAX 和 80386 PC 等多种机器上的专家系统开发环境；Feigenbaum 本人还参与创办了 Teknowledge。1987 年，业界编了一本商业专家系统目录；Gill 1995 年追踪其中约 80 个系统，发现多数在 1987–1992 年间被弃用，约三分之一活了下来。2015 年，Google 的 Sculley 等人在 NeurIPS 发表《Hidden Technical Debt in Machine Learning Systems》，第一次系统地把 ML 系统的维护债写成论文；2017 年，Google Cloud 的官方博客展示开发者如何用 Cloud Vision API 在营销页面里做人脸检测。

## 为什么是这个时候

1980 年代凑齐的是「便宜不了」的三件套：企业有大量重复决策（配置订单、报税、授信），Lisp 工作站和专家系统外壳让符号规则能跑，知识工程师这个新职业负责把老师傅脑子里的经验抄成规则。但硬件贵、规则手工维护、每换一个业务就要重来一遍。到 1990 年前后，通用 PC 性能上升、Lisp 机器性价比崩塌，加上一批系统上线后没人维护，市场从预测的 40 亿美元缩到约 6 亿美元。2010 年代凑齐的是另一套：GPU、ImageNet 之后的预训练模型、云计算和 REST API。模型不再装进企业的机房，而是留在厂商的数据中心，开发者发一个 HTTP 请求就能拿到 JSON 结果。技术门槛从「会写 Lisp」降到「会调接口」，但数据管道、版本管理、线上监控这些脏活并没有消失，只是从实验室搬到了运维团队。

## 怎么工作

专家系统的核心是一台「规则推理机」：知识工程师先访谈领域专家，把经验写成 IF 条件 THEN 结论的规则库；推理机前向链（从事实推结论）或后向链（从目标找证据）地跑，遇到冲突按优先级选规则，最后给出建议并解释「我为什么这么推」。XCON 干的就是这件事：客户订单进来，它按 VAX 的部件兼容表逐条匹配，选 CPU、内存、外设，检查冲突。KEE 则把对象、规则、图形界面和真值维护系统打包，让企业不用从零写推理机。大白话：规则库像把老师傅的「if 看到这个、就加那个」抄成一本菜谱；菜谱能复现招牌菜，但换一批食材、换一口灶，得有人重新试。兜底一句：规则库是人工编码的领域知识，覆盖有限、冲突要调度、维护靠人。API 的工作方式相反：模型、特征管道和算力都在厂商侧，开发者只发请求。大白话：API 像把发电厂接进墙上的插座——你不用自己建电厂，插上就有电；准确地说，它把训练好的模型封装成网络服务，模型、算力和运维留在厂商侧，按调用计费。好处是接入快，坏处是模型成为「未申报的依赖」——它什么时候更新、对哪些输入失效，调用方往往不知道。Sculley 等人把这类问题归成边界侵蚀、纠缠、隐藏反馈回路、未申报消费者、数据依赖、配置债等几类，并指出真实 ML 系统的维护成本常常远超一次性开发成本。

## 它改变了什么

第一，它把「AI 公司」这个物种造了出来。1980 年代，Intellicorp、Teknowledge、Inference 等公司卖开发环境、卖咨询、卖规则库，企业第一次为「知识」单独付钱；但 Gill 的追踪显示，1987–1992 年间多数系统被弃用，原因不是技术指标不达标，而是用户不接受、留不住开发者、从开发转维护失败、组织优先级变化——也就是产品化的四条河。第二，它留下了「知识工程」的方法：先访谈、再建模、再验证，这套流程后来变成需求分析和领域建模的一部分。第三，2010 年代的 API 化把 ML 变成基础设施：Cloud Vision API 用一个 HTTP 请求返回物体、人脸、地标、文字标签的 JSON，小团队不必训练模型也能做人脸检测；代价是模型行为由厂商定义，成本从「买服务器」变成「按调用付费」，责任从「自己调参」变成「看服务条款」。

## 今天的地位

专家系统没有死，只是退到窄而硬的场景：电信设备配置、税务计算、信用授权、保险理赔规则，今天仍大量以规则引擎、决策表、业务规则管理系统的形式存在——因为规则可审计、可解释、改一条就能上线。真正被 API 取代的是「通用推理演示」：今天一个开发者接大模型 API，几分钟就能做出上一代专家系统要写半年的问答 demo。但产品化的门槛反而更清楚了：demo 只看「一次输出对不对」，产品要问「一百万次里错多少次、错了谁负责、数据漂移后谁来修、调用成本能不能覆盖客单价」。2015 年那篇技术债论文之所以被反复引用，就是因为它把「模型只是系统里的一小块」说透了。

## 争议与局限

争议不在「专家系统有没有用」，而在「为什么总在演示里有用、在报表里没用」。Gill 的结论很刺：多数失败不是技术性能或经济目标没达成，而是管理问题——用户不接受、开发者流失、开发转维护断裂、组织换优先级。Sculley 等人则从工程侧补刀：ML 系统会悄悄积累技术债，数据依赖、反馈回路和配置错误能在没人改代码的情况下让指标烂掉。还有一条更硬的：责任。专家系统给医生、信贷员、操作员一个建议，出错时责任仍在人；API 给开发者一个概率输出，出错时责任在谁——厂商、调用方，还是最终用户？这个问题在 1980 年代没解决，在 2010 年代只是换了个界面。成本也常被低估：规则库要人维护，模型要人监控，API 要人付账单，三样都不在 demo 的预算里。

## 关系

本章是《智能与产业》的开篇，把「demo 与产品之间的河」先画出来。后继 b10-c2《推荐系统》是这条河上第一座真正跑通的大桥：Amazon 2003 年的物品协同过滤、YouTube 2016 年的两段式深度推荐，都靠数据飞轮、线上 A/B 和持续运维，而不是靠一个漂亮的离线指标。再往后 b10-c3《自动驾驶》会把同一道题放到更难的路面上：安全责任、长尾数据和实时性。跨书看，它也照应 b9-c8《脑机接口》——医疗器械的「拿证」与软件的「上线」是同一类产品化门槛。
