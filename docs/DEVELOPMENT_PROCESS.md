# 开发流程 · 机忆书库

> 本文档在项目归档时汇总，记录机忆书库从零到上线的实际开发流程、质量门禁、协作方式与运维方案，供复现、交接与后续维护参考。

## 1. 项目目标

机忆书库是一个以 AI 知识为主题的档案馆式网站：把 56 本书、448 章内容组织进一座可漫游的 3D 图书馆，用检索、书轨、星图、时间轴与馆藏玩法连接知识点，并用「暗门 / 假如之书 / 未写之书」承载推测性内容。

核心约束：

- 内容必须可核验，推测与事实明确分开。
- 无前端构建步骤，浏览器直接加载原生 HTML/JS 与本地 vendor。
- 访客可读全部内容，登录后才可盖章、批注、记录进度。
- 移动端可用，低配设备自动降级。
- 部署在现有服务器的 `/ai/` 子路径，不额外购买域名。

## 2. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | 原生 HTML/JS + three.js + Rapier | 无构建、部署简单；3D 与物理能力足够 |
| 后端 | Fastify 5 + Node 内置 `node:sqlite` | 轻量、启动快；Node ≥ 22.5 自带 SQLite |
| 内容 | Markdown + YAML frontmatter + JSON 数据 | 内容即数据，便于校验与批量生产 |
| 检索 | 服务端倒排索引（中文二元组 + 英文词） | 无需外部搜索服务，毫秒级响应 |
| 测试 | `tools/verify.mjs` + `tests/e2e.mjs` | 内容校验与真实浏览器端到端 |
| 部署 | systemd + nginx 反代 | 单机可维护，支持子路径与 HTTPS |

## 3. 阶段化开发

项目按「先数据、再场景、再内容、后玩法与打磨」的顺序推进，每阶段有明确出口。

| 阶段 | 目标 | 主要产出 | 出口 |
|---|---|---|---|
| 1 | 数据与后端 | 数据契约、Fastify 服务、SQLite、检索、样章 | 注册/登录/检索跑通，verify 全绿 |
| 2 | 3D 阅览室 | three.js 场景、物理书架、取书翻开、电梯、阅读三栏 | 端到端可完成「进馆→取书→阅读→返回」 |
| 3 | 内容生产 | 56 本 × 8 章 = 448 章，9 段结构 | 字数、来源、关系全部通过 verify |
| 4 | 探索视图 | 书轨、时间轴、星图、楼层平面图 | 三种路径均可定位并打开章节 |
| 5 | 馆藏玩法 | 残页、失窃页、躁动书页、借阅徽章、暗门 | 收集/追回/归位/分岔状态可持久化 |
| 6 | 视觉与性能 | 写实光影、材质反射、移动端降级、静态合批 | 桌面与手机可读，性能预算内 |
| 7 | 部署与运维 | systemd、nginx、HTTPS、定时任务、备份 | 线上可访问，每日更新与备份正常 |

## 4. 内容生产流水线

1. **先定目录与契约**：`docs/TOC_EXPANSION.md`、`docs/TOC_EXTRA_12.md` 固定书名、索书号、楼层与章节主题；`docs/DATA.md`、`docs/API.md`、`docs/CONTENT.md` 固定字段与写作规范。
2. **统一九段结构**：一句话 → 时间·人物·机构 → 为什么是这个时候 → 怎么工作 → 它改变了什么 → 今天的地位 → 争议与局限 → 关系 → 档案。
3. **字数与来源**：每章 1500–2500 汉字，至少 3 条实际打开核验的来源，frontmatter 标记 `checked: true`；打不开的来源换掉或删除，不编造。
4. **科普表达**：每章至少 2 处「大白话讲解」，页边注用馆员调侃体，但事实主张必须以正文与来源为准。
5. **关系双向**：相关章节互相引用真实 id；索书号唯一；新增书必须同步补 `graph.json` 关系边。
6. **分批生产**：多智能体并行写作，每批完成后统一跑 `npm run verify`，通过后再提交，避免错误跨批累积。

## 5. 质量门禁

### 内容校验

```bash
npm run verify
```

检查章节字段完整、字数、来源数量与核验标记、关系双向、索书号唯一等。归档要求为 0 FAIL。

### 端到端测试

```bash
npm run test:e2e
```

使用本机 Chrome/Edge 覆盖：门厅与登录、三视图切换、取书与阅读、检索与补全、书轨/星图/时间轴、馆藏玩法、移动端布局、性能冒烟与无 JS 报错。

### 性能预算

- 3D 静态网格合批，控制 draw call 数量。
- 手机或低内存设备关闭阴影、降低 DPR、跳过 Rapier 物理包。
- Rapier 延迟到首帧后加载，避免阻塞入场。
- 静态资源使用 ETag / 长缓存，vendor 目录 immutable。

### 安全

- 口令使用 `crypto.scrypt`（N=16384, r=8, p=1，16 字节盐，64 字节输出），校验用 `timingSafeEqual`。
- 会话使用 HttpOnly Cookie，前端不存 token。
- 注册/登录限流；批注长度限制；统一安全响应头。
- `.env`、`.data`、`node_modules`、日志与打包产物不进入仓库。
- 未写之书接口先做格式校验与限流，再调用模型；密钥只从 `.env` 读取。

## 6. 并行协作方式

- 内容生产以 5 个后台智能体为一波，每个智能体负责 4 章或一本，按目录严格取题。
- 一波完成后统一校验、统一提交，再启动下一波；问题当场回写项目档案。
- 代码改动遵循「先验证再声明完成」：未跑 verify / E2E 或未实际打开页面验证，不标记完成。
- 重要决策、踩坑与部署步骤写入项目档案与 `docs/`，避免只存在于会话记忆里。

## 7. 部署与运维

- 运行环境：Node.js ≥ 22.5，生产使用 `npm ci --omit=dev`。
- 进程：systemd 单元 `machine-memory`，`PORT=3300`、`HOST=127.0.0.1`，代码位于 `/opt/machine-memory`。
- 反向代理：nginx 将 `/ai/` 转发到 3300，保留 `wasm-unsafe-eval` CSP 以支持物理引擎。
- HTTPS：使用 IP 证书，定时续期；HTTP 入口保留为备用。
- 定时任务：
  - 每日 04:17 拉取 arXiv、编译前沿科普、更新每周热点。
  - 每日 03:40 备份 SQLite 与内容到 `/opt/mm-backups`，保留 14 天。
- 发布方式：`git archive` 打包 → scp → 解包 → `systemctl restart machine-memory`；`.env` 单独传输并保持 600 权限。

## 10. 经验与教训

- **复杂度要持续压制**：内容、视图、玩法都遵循「深模块」思路——对外接口尽量简单，把复杂性留在实现内部。
- **先测量再优化**：性能优化以实测数据为准，合批、延迟加载、缓存头都先定位瓶颈再动手。
- **移动端单独设计**：不是简单缩放，而是独立的轻量模式与交互（虚拟摇杆、默认书架视图、跳过物理）。
- **内容质量靠门禁**：来源核验、字数、关系双向、索书号唯一必须自动化检查，不能只靠人工记忆。
- **事实与推测分离**：前沿观察、假如之书、未写之书都明确标注性质，避免读者把生成内容当成已核验事实。
- **归档也是流程的一部分**：代码、内容、文档、部署脚本同仓库保存，本地环境可丢弃，仓库即事实来源。
